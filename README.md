# appshelf

[English](README.en.md)

Своя полка приложений iPhone. IPA из истории покупок вашего Apple ID скачиваются на ваш Linux-сервер,
а на iPhone и iPad ставятся прямо из Safari по системной ссылке `itms-services`: без компьютера,
кабеля и iMazing. Главный сценарий — приложения, удалённые из App Store (российские банки, VK и
другие). Apple их больше не показывает, но у кого они есть в покупках, тот по-прежнему может их скачать.

> appshelf работает только с вашими собственными покупками и не снимает DRM: IPA привязаны к вашему
> Apple ID и запускаются на устройствах, где выполнен вход тем же Apple ID в «Контент и покупки».
> Проект не связан с Apple.

## Возможности

- Вход в панель — вашим Apple ID и паролем от него (и код 2FA); пароль нигде не сохраняется. Пользоваться могут
  несколько человек, в одном браузере — несколько Apple ID сразу: у каждого Apple ID своя полка; новые Apple ID —
  по ссылке-приглашению владельца или из панели уже вошедшего участника.
- История покупок: публикуете только то, что выбрали. Удалённое из App Store добавляется по ссылке
  `apps.apple.com/…/id…` или по ID.
- Справочник ~480 удалённых из App Store приложений (банки и их клоны, VK, Почта Mail.ru и другие):
  appshelf проверяет, на какие из них у вашего Apple ID есть лицензия.
- Каталог с кнопкой «Установить»; хранятся текущая и предыдущая версии, а одну из них можно закрепить — она
  переживёт следующие обновления. Поверх установленного iOS не ставит — приложение сначала сгружают (раздел
  «Обновление установленного приложения»).
- Ночная проверка новых версий (скачанные за неделю отмечены в каталоге: удалённое из App Store обновляют
  только отсюда); владельцу — письмо, если истёк вход его Apple ID или кончается место.
- PWA: полка на экране «Домой».
- Android: раздел с Android-полкой участника — APK из RuStore, Google Play, AppGallery, F-Droid, APKPure, по прямой
  ссылке с сайта банка или своим файлом; установка и обновление из браузера телефона, ночная проверка новых версий,
  правило подписи (раздел «Android»).
- Публичная Android-полка: наполняет владелец, гость открывает её по PIN из 6 цифр и только ставит; защита от
  перебора.

## Как устроено

    iPhone (Safari) ─► Apache (HTTPS), vhost apps.example.com
                         ├─ /        → unix:/run/appshelf/web.sock (appshelf-web: вход Apple ID — /login)
                         ├─ /join/, /l/ → без входа (приглашение, запасная ссылка)
                         ├─ /healthz → без пароля (мониторинг)
                         ├─ /pwa/    → без пароля (манифест PWA, иконка)
                         └─ /d/      → <архив>/ без пароля (manifest, IPA, иконки; путь с секретным токеном)
    appshelf-web (обработчик заданий) ─┐
    appshelf-nightly (04:30)           ┴─► bin/ipatool (HOME=/etc/appshelf/accounts/<id>, flock locks/<id>.lock) ─► Apple
                                       └─► android/net.py (только https и глобальные адреса) ─► RuStore, Google Play,
                                           AppGallery, F-Droid, APKPure, сайты (APK)

IPA скачивает `bin/ipatool` — форк [ipatool-cpp](https://github.com/Sorvigolova/ipatool) с нашими патчами
(`ipatool/`): пароль не хранится и передаётся только через stdin, есть команда `list-purchases`, коды
выхода для обёртки. Веб-часть — FastAPI и Jinja2, данные — SQLite. Дизайн —
[docs/superpowers/specs/2026-10-05-appshelf-design.md](docs/superpowers/specs/2026-10-05-appshelf-design.md).
Вход и несколько Apple ID — [docs/superpowers/specs/2026-10-08-multi-apple-id-design.md](docs/superpowers/specs/2026-10-08-multi-apple-id-design.md).

| Что | Где |
|---|---|
| Код, `.venv`, `bin/ipatool` | `/var/_sh/appshelf`, владелец root: appshelf только читает и исполняет (путь зашит в `deploy/*.service` и скриптах `deploy/`) |
| Данные | `/var/lib/appshelf`: `appshelf.db`, `tmp/`, `locks/`, `status/nightly.stamp`, `cookie-key` |
| Архив IPA | `<архив>/<токен полки>/`: у каждого Apple ID свой случайный токен (`accounts.shelf` в базе; Apple ID, перенесённый из первой версии, — `<архив>/<PUB_TOKEN>/`); `<архив>` — `APPSHELF_PUB` или `/var/lib/appshelf/pub`. Может быть сетевой шарой — тогда `APPSHELF_PUB` — подкаталог внутри неё, не сама точка монтирования (пустая точка монтирования — тоже каталог, и IPA легли бы на локальный диск). База и `tmp/` — только локально (SQLite на CIFS портится) |
| Настройки | `/etc/appshelf/appshelf.env` (образец — `deploy/appshelf.env.example`), токены App Store — `/etc/appshelf/accounts/<id>/.ipatool/` |
| Службы | `appshelf-web.service`, `appshelf-nightly.service` + `.timer` |

## Требования

- Linux-сервер (проверено на Debian 13), Python ≥ 3.11 с `venv`.
- Apache 2.4 с `mod_ssl`, `mod_proxy`, `mod_proxy_http`, `mod_headers` и домен с действительным
  HTTPS-сертификатом: iOS ставит по `itms-services` только с доверенного HTTPS.
- Docker — только для сборки `bin/ipatool`: на сервере или на отдельном хосте (`APPSHELF_BUILD_SSH` в `.env`)
  с sudo без пароля; на сервере нужен пакет `libunicorn2t64`.
- Необязательно: локальный `sendmail` (например, exim4) для писем.

## Установка

Команды на сервере — от пользователя с sudo.

1. Пользователь и каталоги. Каталог кода — root: appshelf его только читает и исполняет.

       sudo useradd --system --home /var/_sh/appshelf --shell /usr/sbin/nologin appshelf
       sudo install -d -o root -g root -m 0755 /var/_sh/appshelf /var/_sh/appshelf/bin
       sudo install -d -o appshelf -g appshelf -m 0711 /var/lib/appshelf /var/lib/appshelf/pub /var/lib/appshelf/status
       sudo install -d -o appshelf -g appshelf -m 0700 /var/lib/appshelf/tmp
       sudo install -d -o root -g appshelf -m 0711 /etc/appshelf
       sudo install -d -o appshelf -g appshelf -m 0700 /etc/appshelf/accounts /var/lib/appshelf/locks

2. Python: `sudo python3 -m venv /var/_sh/appshelf/.venv` (от root, как и всё в каталоге кода).

3. Настройки: `deploy/appshelf.env.example` → `/etc/appshelf/appshelf.env` (`root:appshelf 0640`),
   заполнить `PUB_TOKEN` (`python3 -c "import secrets; print(secrets.token_hex(16))"`),
   `APPSHELF_PUBLIC_BASE`, `MAIL_TO`, `APPSHELF_OWNER` (ваш Apple ID).

4. Код и службы: на своей машине `.env` по образцу `.env.example` и `bash deploy/deploy.sh` (код,
   зависимости, юниты; предупредит, что `bin/ipatool` ещё не собран), затем на сервере
   `sudo systemctl enable appshelf-web && sudo systemctl enable --now appshelf-nightly.timer`.

5. `bin/ipatool`: на своей машине `bash deploy/build-ipatool.sh` → `OK: /var/_sh/appshelf/bin/ipatool`.

6. Apache: vhost по образцу `deploy/apache-appshelf.conf` (домен, сертификат, путь архива), затем
   `sudo a2enmod ssl proxy proxy_http headers && sudo apache2ctl configtest && sudo systemctl reload apache2`.
   Проверка: `https://<домен>/healthz` → 200, `/` → форма входа.

7. Первый вход: откройте сайт и войдите Apple ID из `APPSHELF_OWNER` (пароль и код 2FA) — вы владелец.
   Участников приглашайте на странице «Участники».

**Права.** Код, `.venv` и `bin/` — root (`deploy/install.sh` ставит это при каждой выкладке): иначе любое
выполнение кода от appshelf (картинка из IPA, ipatool) стало бы root при ближайшей выкладке или сборке.
Группа кода (`APPSHELF_CODE_GROUP` в `.env`) получает только чтение, appshelf в неё не входит. Службы видят
`/usr` и `/etc` только для чтения, кроме `/etc/appshelf/accounts` (`ProtectSystem=full`).
`/var/lib/appshelf` и `status/` — `0711`: Apache и мониторинг проходят, не читая список.
`/etc/appshelf` — `root:appshelf 0711`, Apache не читает `appshelf.env`. **www-data не входит в группу
`appshelf`**: к сокету Apache пускает группа `www-data` на `/run/appshelf` (`ExecStartPost` в юните),
иначе RCE в любом PHP-сайте на сервере читало бы `PUB_TOKEN` (`deploy.sh` это проверяет). Архив на шаре
открыт тем, кому его открывает монтирование; от интернета его закрывают `-Indexes` и токен в ссылке.

## Выкладка и сборка

    bash deploy/deploy.sh                                          # код + перезапуск; куда — .env (.env.example)
    bash deploy/build-ipatool.sh                                   # bin/ipatool (после правки ipatool/ и выкладки)

Уезжает закоммиченный `HEAD` (`git archive`): с незакоммиченными правками в коде `deploy.sh` откажется. Новый
код встаёт на место прежнего целиком и только после `pip`; откат — выложить прежний коммит (через переход схемы
базы — только если переход объявил её годной прежнему коду, см. `SCHEMA_VERSION` в `store.py`). Если `bin/ipatool`
собран не из выложенных патчей, `deploy.sh` напомнит о пересборке; когда пересобирать без правок —
[ipatool/README.md](ipatool/README.md). `build-ipatool.sh` собирает выложенные на сервер `ipatool/`, в
одноразовом контейнере `debian:trixie` на хосте `APPSHELF_BUILD_SSH` (не задан — на самом сервере), и ставит
бинарник на сервер, только если там хватает библиотек.

## Вход и участники

Вход в панель — Apple ID и паролем от него, затем код 2FA. Пароль не сохраняется: в ipatool он идёт через
stdin, в appshelf-web живёт в памяти не дольше 10 минут. Вход запоминается на год; «Выйти на всех
устройствах» (страница «Аккаунты») гасит все cookie человека. Можно войти и Google-аккаунтом — «Вход через Google»
ниже.

Новый Apple ID попадает на сервер только по ссылке-приглашению: «Участники» → «Создать ссылку». Ссылка
работает, пока её не отключили или не удалили, — одна на всех или своя на каждого; спрашивается один раз, при
первом входе. Отключённая остаётся в списке, удалённая пропадает из него.
Ещё один Apple ID вошедший участник добавляет сам, без приглашения: «Аккаунты» → «Добавить Apple ID». Новый
Apple ID никому не достаётся — он становится отдельным участником: в этом браузере его полка подключается сразу,
на других устройствах им входят отдельно, а владельцу приходит письмо о новом участнике. У каждого Apple ID своя
полка: история, каталог, IPA (в IPA — данные покупателя, ставится он на iPhone с тем же Apple ID в App Store).

В одном браузере можно войти сразу как несколько участников: каждый следующий вход — форма входа, «Добавить
Apple ID» с Apple ID другого участника, приглашение, запасная ссылка — добавляет участника к уже вошедшим, а
меню Apple ID в шапке переключает между полками всех. Так подключают общий Apple ID: он остаётся отдельным
участником, вход им одним открывает только его полку. «Убрать с этого устройства» (страница «Аккаунты») убирает
из браузера одного участника, «Выйти» (то же меню) — всех; «Выйти на всех устройствах» гасит одного участника
везде.

Истёк токен магазина — баннер на полке и «Войти заново»; владельцу — письмо о его Apple ID. Если Apple сломает
вход — запасная ссылка (одноразовая, 24 ч; открывает страницу с кнопкой «Войти», так что превью мессенджера
её не расходует): «Участники» → «Ссылка входа» или на сервере

    sudo -u appshelf bash -c 'set -a; . /etc/appshelf/appshelf.env; set +a; /var/_sh/appshelf/.venv/bin/appshelf login-link --email <Apple ID>'

Для Apple все входы идут с сервера: клиент — Apple Configurator на Mac, место на карте запроса входа — по IP
сервера. У каждого нового Apple ID свой MAC (`IPATOOL_DEVICE_MAC`, патч 05) — для Apple это отдельный «Mac».

Консольный `auth login` годится лишь для проверки форка: сайт о нём не узнаёт, поэтому задания и ночная
проверка стоят, пока не выполнен вход в панели. Если всё же нужен — только от `appshelf` и под блокировкой
этого Apple ID (иначе служба не прочитает учётку или столкнётся с идущим скачиванием):

    sudo -u appshelf env HOME=/etc/appshelf/accounts/<id> IPATOOL_DEVICE_MAC=<accounts.device_mac, если не пуст> flock /var/lib/appshelf/locks/<id>.lock /var/_sh/appshelf/bin/ipatool auth login -e <Apple ID>

Учётка ipatool — файл `$HOME/.ipatool/account`, и требования к запуску тут разные по причине:
- `HOME` только выбирает, чью учётку взять: у каждого Apple ID свой `accounts/<id>`. В ключ шифрования путь
  не входит — готовую `.ipatool` можно перенести в другой `HOME` на этой же машине.
- Ключ — PBKDF2 от `machine-id`, passphrase (у appshelf пустой) и соли из самого файла. У root к `machine-id`
  добавляется `product_uuid`, который читает только root: учётку, сохранённую от root, служба не расшифрует, а
  сохранённую службой — root. На другой машине (другой `machine-id`) не расшифровывается ни одна.
- Файлы учётки — `appshelf`, `0700`/`0600`: другой пользователь, кроме root, их не прочитает.

### Вход через Google

«Войти через Google» на странице входа — OpenID Connect (Authorization Code + PKCE). Пароль Google вводится на
странице Google: сервер получает только личность аккаунта (`sub`, адрес, имя) — ни пароля, ни доступа к Google.
Кнопка есть, когда в `appshelf.env` заданы `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`; без них `/google/*` — 404.

Клиент OAuth владелец заводит один раз (бесплатно; для `openid email profile` проверка приложения Google не нужна):

1. [Google Cloud Console](https://console.cloud.google.com/) → новый проект.
2. «APIs & Services» → «OAuth consent screen»: тип External, статус In production; scope — только `openid`, `email`,
   `profile` (чувствительных нет). Без домашней страницы (`<адрес сайта>`), ссылки на политику конфиденциальности
   (`<адрес сайта>/privacy` — страница appshelf, открывается без входа) и домена сайта в Authorized domains
   «Publish app» не включается. Учётке Google для Cloud Console нужна двухэтапная аутентификация.
3. «Credentials» → «Create credentials» → «OAuth client ID»: тип Web application, Authorized redirect URI — ровно
   `<адрес сайта>/google/callback` (`APPSHELF_PUBLIC_BASE` + `/google/callback`).
4. Client ID и Client secret — в `/etc/appshelf/appshelf.env` (`GOOGLE_CLIENT_ID=`, `GOOGLE_CLIENT_SECRET=`; секрет —
   только там), затем `sudo systemctl restart appshelf-web`.

Как с Apple ID: новый Google-аккаунт попадает на сервер только по ссылке-приглашению или из «Аккаунты» → «Добавить
Google» вошедшего участника — и всегда отдельным участником; владельцу приходит письмо. Вход добавляет участника к
вошедшим в браузере. У участника только с Google-аккаунтом Apple-раздел пуст — «Добавить Apple ID» на странице
«Аккаунты». Android-раздел показывает полку одного из вошедших; выбор — в меню шапки раздела, там же «Публичная».

**«Связать».** Когда в браузере вошли двое и хотя бы у одного нет Apple ID, на странице «Аккаунты» есть «Связать»:
Google-аккаунты и Android-полка второго переходят к первому, второй участник удаляется, вход любым их аккаунтом
открывает все полки первого. Кто остаётся, решает сервер: участник с Apple ID; без Apple ID у обоих — владелец, иначе
тот, кто вошёл в этом браузере раньше. Приложение, которое есть на обеих Android-полках, остаётся у остающегося.
Связку не отменить. Двух участников, у каждого из которых есть Apple ID, не связать, и Apple ID к другому участнику
не переходит никогда: общий Apple ID открыл бы чужие личные полки. Аккаунт, которым пользуются несколько человек,
не связывайте.

Удалить Google-аккаунт — «Аккаунты» → «Удалить»; был последним аккаунтом участника — участник удаляется вместе с
Android-полкой. Удалённый Google-аккаунт можно добавить снова — отдельным участником.

Веб-приложение с экрана «Домой» iPhone хранит cookie отдельно от Safari, и возврат от Google может прийти в Safari, а
не в него; тогда входите в нём Apple ID или откройте страницу в Safari.

## Удалённые из App Store приложения

В истории покупок, которую отдаёт Apple (DAAP, как у Apple Configurator), их нет — даже если лицензия
есть и по id приложение скачивается. Банки к тому же выпускали десятки клонов под чужими названиями.
Поэтому «Обновить историю» ещё и проверяет справочник `appshelf/data/removed_apps.json` (источники — в поле
`source`) по Apple ID: свои добавляются в «Историю» с меткой «удалено из App Store». Кнопка не перепроверяет
то, на что лицензии не было, — это делает ночная проверка раз в неделю, в свой день недели Apple ID; тогда же
она дозаполняет версии. Весь справочник с отметкой «есть / нет в аккаунте» — страница «Удалённые»
(`/blocked`); там же поле «Добавить»: ссылка
`apps.apple.com/…/id492224193` или ID, имя подставится из IPA. Пополнить справочник — дописать
`{"id", "name", "aliases"}` в JSON (алиасы — для поиска латиницей: vk, sber…). Снят ли ID с RU App Store —
`itunes.apple.com/lookup?id=…&country=ru` (пусто — снят).

Проверка справочника по кнопке идёт минуты (~480 запросов) и уступает очередь публикации. Пока идёт, «Удалённые» и
«История» показывают «проверено X из Y: найдено …, нет лицензии …, ошибок …» — ход хранится в задании
(`jobs.progress`) и переживает перезагрузку страницы и уступку очереди. После окончания «Удалённые» показывают итог
последней проверки, а ID, на которых Apple ответил технической ошибкой, помечены «ошибка проверки» — отдельно от
«нет в аккаунте»; следующая проверка спросит их снова.

В каталоге у версии — дата сборки: время `Info.plist` в IPA. `releaseDate` Apple (и в
`get-version-metadata`, и в `iTunesMetadata.plist`) — дата первого выпуска приложения, не версии.

## Обновление установленного приложения

Поверх уже установленного приложения iOS по `itms-services` не ставит: на «Установить» отвечает окном
«… is Already Installed» с советом удалить приложение. Версия и Apple ID тут ни при чём: iOS решает до
скачивания, по одному идентификатору приложения. Удалять не нужно — приложение сгружают: «Настройки → Основные →
Хранилище iPhone» → приложение → «Сгрузить приложение», затем «Установить» в каталоге. При сгрузке iOS убирает
программу и оставляет её данные, поэтому встаёт версия с полки с прежними данными. Сгруженное приложение,
удалённое из App Store, значок на экране «Домой» не вернёт — только «Установить» с полки.

Закреплённая версия («⋯» → «Закрепить», одна на приложение) не удаляется при обновлениях: выйдя из текущей и
предыдущей, она остаётся в каталоге «сохранённой» с обычной ссылкой установки и занимает место в архиве, пока
закрепление не снимут. Сохранён только файл: откат на старую версию не гарантирует, что приложение примет данные,
оставленные более новой, — ставить её поверх них (сгрузив новую) на свой риск.

«⋯» → «Проверить обновление» запрашивает у Apple последнюю версию одного приложения сразу, без ночи и без проверки
истории и справочника; повторные нажатия не ставят второе задание, без входа в Apple ID оно ждёт входа. Отказ Apple
текущую версию не трогает — она ставится. У карточки — итог последней проверки (кнопкой или ночью): «проверено
ДД.ММ ЧЧ:ММ UTC — новее нет / скачана новая версия / не удалось: …»; это о полке, не о версии на телефоне.

## Android

Тот же сервер держит и Android-полки: раздел **Android** в панели, переключатель Apple/Android — в шапке. С телефона
Android панель открывается сразу в нём, с iPhone — в Apple, с компьютера — в разделе, открытом последним.
Android-полка — у участника, а не у Apple ID: APK ни к какому аккаунту не привязан. Дизайн —
[docs/superpowers/specs/2026-10-28-android-design.md](docs/superpowers/specs/2026-10-28-android-design.md)
(реализованы этапы 1–5: RuStore, прямая ссылка, свой файл, публичная полка по PIN, вход через Google и «Связать»,
Google Play — бесплатные приложения одним APK, AppGallery, F-Droid, APKPure).

- **Источники.** «Добавить» → поиск в RuStore (универсальный APK; подпись сверяется с той, что сообщает RuStore;
  платные недоступны), Google Play — подключённым Google-аккаунтом (ниже), «По ссылке» — страница приложения в Google
  Play, AppGallery (или её ID вида `C102312137`), F-Droid, APKPure, RuStore (источник и пакет берутся из адреса) или
  прямая ссылка `https` на APK с сайта банка или разработчика, «Свой файл» — загрузка до 1 ГБ. Во внутреннюю сеть
  сервер по ссылке не ходит: имя резолвится перед каждым запросом и после каждого редиректа, и любой не глобальный
  адрес (частный, loopback, link-local, multicast) — отказ до соединения.
- **Ограничения источников.** Только один целый APK, платное — нигде, кроме купленного в Google Play. Правила RuStore,
  AppGallery, APKPure и Google Play запрещают автоматическое скачивание: запросы идут по одному, с паузой, ночью —
  раз в сутки; риск блокировки доступа принимает владелец сервера.
- **Установка.** «Скачать APK» в Chrome на телефоне; в первый раз Android попросит разрешить установку из
  браузера. Обновление — тот же «Скачать APK» поверх установленного, данные приложения остаются. Браузер ставит
  только один целый APK: наборы (split APK, XAPK, APKS) отклоняются при добавлении. «Скопировать ссылку» в «⋯» карточки —
  постоянный адрес `<адрес сайта>/apk/<токен полки>/<пакет>.apk`: всегда текущая версия, открывается без входа (как сами файлы);
  смена токена полки (`rotate-token`, новый PIN публичной) отключает и его.
- **Подпись.** Первая версия задаёт подпись приложения на полке. Новая версия с другим сертификатом текущей не
  становится: на карточке «подпись сменилась» и «Принять новую подпись» — поверх установленной такая версия не
  встанет, приложение придётся удалить вместе с данными. Стояло из Google Play с другой подписью — сначала удалить.
- **Версии** — как у IPA: текущая, предыдущая, закреплённая; «⋯» — проверить обновление, закрепить, сменить
  источник, загрузить новую версию файлом, снять с полки. Хранение —
  `<архив>/<токен Android-полки>/<пакет>-<versionCode>/{<пакет>-<версия>.apk, icon.png}`.
- **Ночная проверка** — после Apple ID, и без входа в Apple ID тоже: RuStore, Google Play, AppGallery и APKPure — по
  `versionCode`, F-Droid — по рекомендуемой версии, ссылка — по `ETag`, `Last-Modified`, `Content-Length`; свой файл
  ночью не проверяется. В итоге ночи — «Android: обновлено N, без изменений M, ошибок K».
- **Сертификаты НУЦ.** CDN RuStore, сайты Сбера и ВТБ — с сертификатом НУЦ Минцифры, которому системные корни не
  доверяют. Загрузчик APK (и только он) берёт дополнительные сертификаты из файла `APPSHELF_SOURCES_CA`, проверка
  сертификата не отключается: Russian Trusted Root CA (`gu-st.ru`) и, для Газпромбанка, чей сервер не отдаёт
  цепочку, промежуточный LiteSSL RSA CA 2025. Без файла RuStore не скачивает.
- **Apache.** В `<Directory>` архива — `AddType application/vnd.android.package-archive .apk` и
  `Content-Disposition: attachment` для `.apk` (с `application/zip` Chrome сохраняет `.apk.zip`); для адресов
  загрузки своей и публичной полки — `LimitRequestBody 1100000000`. Загрузка идёт во временный каталог
  `TMPDIR=/var/lib/appshelf/tmp` (в юните `appshelf-web`), не в `/tmp`.

Подсказки на телефоне — в каталоге раздела: Samsung Auto Blocker, Huawei «Режим без угроз», Play Protect; с 2027
года Google требует проверку разработчика и для установки не из магазина — приложения непроверенных разработчиков
(вероятно, и банков под санкциями) ставятся только через разовый «advanced flow» (режим разработчика, сутки ожидания).

### Google Play

Свой небольшой клиент протокола Google Play (`appshelf/android/play.py`), без внешних программ. Качает
Google-аккаунт, подключённый к Play на странице «Аккаунты»; служебного общего аккаунта нет.

- **Подключение** — «Подключить к Google Play» у Google-аккаунта: на компьютере войти этим аккаунтом на
  `accounts.google.com/EmbeddedSetup`, скопировать cookie `oauth_token` (F12 → Application → Cookies) и вставить в
  форму в течение 10 минут. Сервер обменивает его на мастер-токен: адрес аккаунта из ответа Google должен совпасть,
  иначе отказ. **Мастер-токен даёт доступ ко всему Google-аккаунту, не только к Play**, владелец сервера технически
  может им воспользоваться, Google может заблокировать аккаунт за сторонний клиент — страница подключения об этом
  предупреждает. Пароль Google сервер не получает.
- **Где токены.** Мастер-токен и профиль «устройства» — файлы `/etc/appshelf/google/<id>/` (`appshelf`, каталог
  0700, файлы 0600; `deploy/install.sh` создаёт `/etc/appshelf/google`, юниты пишут туда через `ReadWritePaths`),
  токен Play — в памяти процесса. Ни в базе, ни в журнале, ни в argv. «Отключить Google Play» и удаление
  Google-аккаунта удаляют каталог.
- **Одним APK.** На полку — только то, что Play отдаёт одним файлом. Почти всё в Play — App Bundle (split APK): такое
  из браузера не ставится, на карточке — «набором файлов — из браузера не ставится» и, если пакет есть одним APK в
  RuStore (бесплатно), AppGallery или F-Droid, — где именно и «смените источник». Новая версия пришла набором — на
  полке остаётся прежняя с отметкой.
- **Купленное** — только на личную полку того, чей аккаунт купил (проверка на сервере): не на публичную и не на
  чужую. «Мои покупки» появятся после живой проверки покупок через прокси страны аккаунта.
- **Прокси** — для страны аккаунта: `APPSHELF_PROXIES` в `appshelf.env` (`имя=url` через пробел, `http://хост:порт`
  или `socks5h://[логин:пароль@]хост:порт`), выбирает владелец при подключении. Прокси — только для запросов к
  Google Play; недоступен — ошибка у карточки, прямого соединения нет. С российского адреса Play показывает цены в
  рублях и платное не отдаёт.
- **Истекло.** Сменили пароль Google или отозвали доступ — «подключение Google Play истекло»: баннер в разделе
  Android и на «Аккаунтах», задания аккаунта ждут, ночью его приложения пропускаются; письмо — только о
  Google-аккаунтах владельца, одно на эпизод. «Подключить заново» — новый `oauth_token`.
- **Живой тест** — `pytest -m integration tests/test_android_play_live.py` с `APPSHELF_PLAY_TEST_GID=<id
  подключённого Google-аккаунта>` в `.env`: `details` бесплатного пакета от `appshelf` на сервере.

### AppGallery, F-Droid, APKPure

Добавляются «По ссылке» — страницей приложения (поиск — только в RuStore); «⋯ → Сменить источник» переключает
карточку на любой из них по её пакету. С RuStore сверяется подпись каждой скачанной версии.

- **AppGallery** — клиентский API Huawei без входа (`client.updateCheck` по имени пакета: версия, размер и SHA-256
  файла, ссылка на APK); ID со страницы (`appgallery.huawei.com/app/C…`) переводится в пакет. Хост API по умолчанию —
  российский `store-drru.hispace.dbankcloud.ru`, другой — `APPSHELF_APPGALLERY_HOST` в `appshelf.env`. С зарубежного
  адреса AppGallery отвечает другой зоной, банков в ней нет — «AppGallery не нашёл приложение (зона …)». Huawei может
  переподписать приложение своим ключом: подпись не как в RuStore — метка «подписан не так, как в RuStore: не встанет
  поверх версии оттуда» (приложение добавляется).
- **F-Droid** — официальный репозиторий `f-droid.org`: пакетный API и APK по HTTPS. Подпись индекса F-Droid **не
  проверяется** (индекс — десятки МБ JSON): подпись приложения задаёт первая версия на полке, как у ссылки. У одной
  версии бывает несколько сборок по ABI, и рекомендуемая — не обязательно ARM (у VLC — x86_64): полка берёт
  универсальную или `arm64-v8a`, иначе `armeabi-v7a`, иначе — «в F-Droid нет сборки для ARM». Банков в F-Droid нет.
- **APKPure** — API клиента APKPure без входа, только одиночный APK: XAPK — «набором файлов» с подсказкой, где
  пакет есть одним APK. APKPure распространял подменённые APK (2021 — троян в клиенте, 2025 — Telegram X с
  бэкдором), поэтому: пакет есть в RuStore — подпись **обязана** совпасть, иначе «подпись не совпала с RuStore»; нет —
  добавление только с галочкой «понимаю» и меткой «подпись не сверена», дальше — общее правило подписи.

### Публичная полка

Одна Android-полка на сервер для тех, у кого нет входа в панель. Наполняет её владелец (вкладка Android →
**Публичная** → «Добавить в публичную»: те же источники), участники видят её на той же вкладке без
PIN и без действий, гость открывает `<адрес сайта>/p` и вводит PIN — видит только список с «Скачать APK» и
подсказками, без меню и панели.

- **PIN** — 6 цифр, задаёт и меняет владелец в блоке «Гостевой доступ» на вкладке «Публичная». Пока PIN не задан,
  `/p` гостям ничего не показывает. В базе — только соль и хэш (PBKDF2-SHA256, 200 000 итераций), сам PIN нигде не
  хранится. После верного PIN браузер гостя помнит полку 90 дней (cookie, подписанная ключом `cookie-key`).
- **Смена PIN** гасит все cookie гостей и даёт публичной полке новый токен каталога: пересланные раньше ссылки на
  APK перестают работать. Пока идёт скачивание, PIN не меняется — «попробуйте через минуту».
- **Перебор.** 20 неверных PIN с одного адреса за час — адрес закрыт на час (IPv6 — по сети /64). 100 неверных со
  всех адресов за сутки — ввод PIN закрыт для новых гостей на сутки; гости с действующей cookie полку видят. Не 6
  цифр — не попытка. Счётчики — в базе, выкладка их не сбрасывает. Адрес гостя — последний элемент
  `X-Forwarded-For`, который дописывает Apache: перед ним не должно быть другого прокси, иначе все гости делят один
  счётчик.
- **Письмо «ввод PIN публичной полки закрыт»** — одно на эпизод: кто-то подбирает PIN. Открыть ввод сразу —
  «Открыть ввод PIN» на вкладке «Публичная»; если PIN мог утечь — смените его (смена тоже открывает ввод).
- Ссылки на файлы, как и у IPA, работают без PIN: PIN защищает страницу, а не файлы. Купленное на публичную полку
  не попадает.

## На экран «Домой» (PWA)

Safari → «Поделиться» → «На экран „Домой“»: полка открывается без адресной строки. Манифест и иконка
(`/pwa/`, рисует `web/pwa.py`) отдаются без пароля — в приложении и в Apache (`<Location /pwa/>`).
Окно Basic Auth веб-приложение с экрана «Домой» не показывает (401 → чёрный экран), поэтому вход —
формой `/login` с cookie на год. Service worker нет: iOS ставит веб-приложение и без него, а без сети
полка бесполезна.

## Новый токен полки

У каждого Apple ID свой случайный токен каталога в архиве; он же — в ссылках установки и manifest. Утекли ссылки
полки — дайте ей новый токен (каталог переименуется, manifest поправятся, прежние ссылки перестанут работать,
установленные приложения останутся):

    sudo -u appshelf bash -c 'set -a; . /etc/appshelf/appshelf.env; set +a; /var/_sh/appshelf/.venv/bin/appshelf rotate-token --email <Apple ID>'

Android-полкам — так же: `rotate-token --email <Apple ID> --android` — полка участника этого Apple ID,
`rotate-token --public` — публичная (её токен меняет и смена PIN). Каталог переименуется, ссылки на APK на странице
станут новыми, прежние перестанут работать.

`PUB_TOKEN` — каталог только полки, перенесённой из первой версии; после `rotate-token` для неё он не нужен
ни одной полке. Каталоги, которые версия 2 считала HMAC от `PUB_TOKEN`, `appshelf-web` при старте сам переносит
на случайные токены.

## Проверка целостности

    sudo -u appshelf bash -c 'set -a; . /etc/appshelf/appshelf.env; set +a; /var/_sh/appshelf/.venv/bin/appshelf check'

Только чтение: база открывается без записи, в архиве ничего не меняется и не удаляется. По каждой версии в базе —
есть ли каталог, `app.ipa` нужного размера, `icon.png`, разбирается ли `manifest.plist` и ведут ли его ссылки на
эту полку; `--deep` ещё сверяет SHA-256 IPA (сохраняется при скачивании) и itemId, external version id и
bundle id внутри IPA — читает весь архив. Отдельно — каталоги без строк в базе, `.partial` (во время скачивания
это норма), незавершённый перенос полки, каталоги архива без Apple ID. Android-полки — так же: каталог версии,
APK нужного размера, `icon.png`, `--deep` — SHA-256 APK. Apple ID и Android-полки в отчёте — по номеру, токены
полок — `<токен>` или первые четыре символа. `--json` — отчёт для машины. Код выхода: 0 — проблем нет, 1 —
есть, 2 — проверка не выполнена (архив не смонтирован, нет базы).

## Резервная копия

Ночной снимок базы — `appshelf-backup.timer` (05:30, после ночной проверки): `appshelf backup --daily` кладёт
`appshelf-<дата>.db` в `APPSHELF_BACKUP_DIR` и хранит 14 последних. Каталог — не на диске сервера (например, на
шаре рядом с архивом), создаётся один раз заранее от `appshelf`; без строки `APPSHELF_BACKUP_DIR` в `appshelf.env`
`install.sh` таймер не включает. Снимок делается локально и ложится в каталог готовым файлом. Права файлов на
шаре задаёт монтирование: снимок открыт тем же, кому и архив (адреса и имена Apple ID есть и в самих IPA).

Набор восстановления — снимок базы, копия архива и проверка, что из этой пары полка восстанавливается целиком.

1. Снимок базы — командой, не копией файла на ходу (WAL): согласованный, один файл, права 0600. Каталог —
   новый или пустой:

       sudo -u appshelf bash -c 'set -a; . /etc/appshelf/appshelf.env; set +a; /var/_sh/appshelf/.venv/bin/appshelf backup --out /backup/appshelf/2026-10-21'

   В снимке люди, Apple ID, токены полок и перечень версий с размерами и SHA-256.
2. Архив IPA — копией каталога, сразу после снимка: `rsync -a <архив>/ /backup/appshelf/2026-10-21/pub/`.
3. Проверка копии — та же проверка целостности, но по снимку и копии архива (снимок открывается только на
   чтение; Apple и письма не участвуют):

       sudo -u appshelf bash -c 'set -a; . /etc/appshelf/appshelf.env; set +a; /var/_sh/appshelf/.venv/bin/appshelf check --db /backup/appshelf/2026-10-21/appshelf.db --archive /backup/appshelf/2026-10-21/pub --deep'

   Код 0 — набор годен. Пропавшие файлы или каталоги значат, что между снимком и копией ночь сменила версию или
   прошёл `rotate-token`: повторите набор. Снимок от другой версии схемы проверка не примет — проверяйте той же
   версией appshelf, что сняла снимок.

- `/etc/appshelf/appshelf.env` (`PUB_TOKEN`) и `/var/lib/appshelf/cookie-key` — отдельно, в защищённое место: без
  них каталоги архива и вход на устройствах не восстановить как были.
- Учётки ipatool (`/etc/appshelf/accounts`) зашифрованы ключом от `machine-id`: на другой машине они не
  читаются — после переноса каждый Apple ID входит заново, архив переносится вместе с базой и `appshelf.env`.

## Разработка

    python -m venv .venv && .venv/bin/pip install -e ".[test]"   # Windows: .venv\Scripts\pip
