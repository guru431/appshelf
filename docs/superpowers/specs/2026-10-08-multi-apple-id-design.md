# Несколько Apple ID и вход в панель через Apple ID — дизайн

**Дата:** 2026-10-08 · **Статус:** согласован, к реализации · **Основа:** [2026-10-05-appshelf-design.md](2026-10-05-appshelf-design.md)
(что здесь не сказано — как там)

## 1. Зачем

appshelf сделан и проверен для одного человека — владельца сервера: один Apple ID, вход в панель паролем
страниц. Теперь доступ получают коллеги и друзья: у каждого своя полка, у некоторых по нескольку Apple ID.

- Всё — через веб: ни вход в Apple, ни заведение людей не требуют командной строки.
- Новый Apple ID попадает на сервер только по ссылке-приглашению владельца; приглашение спрашивается один
  раз — при первом входе Apple ID, которого на сервере нет.
- Дальше человек входит сам, с любого устройства, сколько угодно раз — **только своим Apple ID и паролем от
  него** (плюс код 2FA, который требует Apple). Других паролей нет: пароль страниц уходит.
- У каждого Apple ID своя полка: история покупок, каталог, IPA. В IPA лежат данные покупателя
  (`iTunesMetadata.plist`), а запускается приложение только на iPhone с тем же Apple ID в App Store,
  поэтому полки разных Apple ID не смешиваются.

### Критерии успеха

1. Владелец создаёт приглашение → человек входит своим Apple ID (пароль → код 2FA) → видит свою историю,
   публикует приложение и ставит его на свой iPhone.
2. Человек с двумя Apple ID переключается между полками без повторного входа; на новом устройстве входит
   любым из них и видит обе.
3. Неизвестный Apple ID без приглашения получает отказ, обращения к Apple не было (подставной ipatool не
   вызван).
4. Участник A не открывает страницы и файлы IPA участника B, даже зная свои ссылки установки.
5. Вход через Apple сломан → владелец выдаёт одноразовую ссылку входа → по ней вход работает.
6. Ночная проверка обходит все Apple ID; истёкший токен одного не останавливает остальные.
7. Нынешние каталог, история и ссылки установки владельца работают после перехода без повторного входа.
8. Пароля Apple ID нет в файлах, логах, `jobs.error`, argv — как и раньше.

### Вне рамок

Квоты на место (владелец видит занятое и может удалить), несколько владельцев и передача роли, письма
участникам, вход по passkey или «Вход с Apple» (Sign in with Apple требует платной программы Apple Developer
и токена магазина всё равно не даёт).

## 2. Решения, принятые при обсуждении

| Вопрос | Решение | Почему |
|---|---|---|
| Кто пользуется | Несколько людей; у человека может быть несколько Apple ID | Требование владельца |
| Модель | Человек (`users`) → его Apple ID (`accounts`) | Вход любым ID открывает все полки человека; владелец отзывает доступ человека целиком |
| Допуск нового Apple ID | Ссылка-приглашение; одна ссылка годится и как общая, и как личная — работает, пока владелец её не отключит | Требование владельца |
| Второй Apple ID человека | Добавляется изнутри панели, без приглашения | Человек уже допущен |
| Обычный вход | Apple ID + пароль (+ код 2FA) через ipatool | Требование владельца: других паролей нет |
| Сессия панели | Cookie на год, не зависит от токена магазина | Истёкший токен не выбрасывает из панели — только баннер «войти заново» |
| Если Apple сломает вход | Одноразовая ссылка входа от владельца: в панели, а если и панель недоступна — `appshelf login-link` по SSH | Не терять доступ к уже скачанному; это аварийный путь, не обычный вход |
| Первый владелец | `APPSHELF_OWNER=<Apple ID>` в `appshelf.env`: вход этим ID без приглашения, пока владельца нет; при переходе — владелец нынешних данных | Без командной строки и без окна, в которое успеет влезть чужой |
| «Устройство» для Apple | Свой MAC на каждый новый Apple ID (патч `05-device-mac`); у перенесённого ID — настоящий MAC сервера | Apple узнаёт устройство по MAC (§3); один «Mac» с десятком Apple ID — то, за что блокируют |
| User-Agent на пользователя | Нет | UA — тип клиента, одинаковый у всех Mac с Configurator; самодельный UA Apple отклоняет на edge |
| Архив | Каталог на каждый Apple ID, токен — случайный, в `accounts.shelf` (*уточнение 2026-10-09*; было — HMAC от `PUB_TOKEN`) | С общим токеном участник подобрал бы путь к чужому IPA; с HMAC `PUB_TOKEN` из ссылки полки владельца раскрывал все полки |
| Справочник удалённых ночью | Полная перепроверка — раз в неделю на Apple ID, по дням недели | ~480 запросов на ID за ночь; с десятью ID — ~4800 с одного IP |

Отвергнуто: «Apple ID и есть пользователь» без сущности человека (на новом устройстве — вход каждым ID с 2FA,
нечего отозвать целиком), общий пароль страниц как запасной вход (владелец: других паролей нет), passkey
(владелец: только Apple ID и пароль), Sign in with Apple (платная программа, оплата из России затруднена).

## 3. Проверенные факты (код форка, 2026-10-08)

- **Как Apple узнаёт устройство.** Вся связь с Apple — с сервера; браузер пользователя видит только
  appshelf. ipatool представляется `Configurator/2.18 (Macintosh; OS X 15.3.2; 24D81)`. Из MAC сетевой карты
  (`device_mac.cpp: device_mac_address()`) получаются: `guid` во входе и в ссылках скачивания, `kbsync`
  (`generate_kbsync`: FairPlay от MAC и DSID), `fserial` (последние 4 байта MAC). `machine-id` к Apple не
  уходит — только шифрует файл учётки. Upstream отказывается подставлять заглушку MAC: «can get the Apple ID
  locked».
- **2FA.** Вход — старая схема «пароль и код подряд» (`do_login`: `password + authCode`). Ожидаем код при
  каждом новом входе: доверие такому клиенту Apple, судя по всему, не запоминает. Проверяется живьём (§13, шаг 1).
  Сервер не становится доверенным устройством Apple ID: доверенные — вошедшие в iCloud.
- **Окно на устройствах человека** — «Запрос на вход с Apple ID» с картой по IP **сервера**.
- **Учётка ipatool** — `$HOME/.ipatool/{account,cookies}`; вне HOME ipatool только читает `machine-id`.
  Разные HOME — независимые учётки, можно запускать параллельно.
- **`auth login --format json`** → `{"name","email","storefront","success"}`; DSID не отдаёт.
  `auth info` (без обращения к Apple) отдаёт то же из сохранённой учётки.

## 4. Вход и сессии

### Сущности (§5): человек `users`, его Apple ID `accounts`, ссылки `links`.

### Приглашение

`/join/<токен>`: ссылка есть и не отключена → cookie `appshelf_invite` (сырой токен, сутки, HttpOnly,
SameSite=Lax) → редирект на `/login` с плашкой «Приглашение принято — войдите своим Apple ID». Иначе — `/login`
с текстом «Ссылка-приглашение недействительна — попросите новую». Перед созданием человека ссылка
проверяется ещё раз.

### Вход `/login`

**Шаг 1 — Apple ID и пароль.** Адрес нормализуется (`strip`, нижний регистр). До обращения к Apple:

| Случай | Решение |
|---|---|
| Apple ID есть в `accounts` | вход в его HOME |
| Нет; действующая cookie приглашения | вход нового ID → новый человек (`member`, `invite_id`) |
| Нет; адрес = `APPSHELF_OWNER` и владельца нет | вход нового ID → владелец |
| Нет; человек уже в панели, «Добавить Apple ID» (`/apple/add`) | вход нового ID → привязать к этому человеку |
| Иначе | «Этот Apple ID на сервере не зарегистрирован — нужна ссылка-приглашение»; Apple не вызывается |

Ключ Apple ID — адрес, которым вошли впервые: вход другим адресом того же Apple ID (алиас, телефон) — как
неизвестный.

**Шаг 2 — код 2FA**, если ipatool вернул `auth_code_required`. Пароль — в памяти `appshelf-web` не дольше
10 минут (как сейчас), но в словаре незавершённых входов под случайным id из cookie `appshelf_login`
(10 минут, HttpOnly). Не больше 20 незавершённых входов одновременно — дальше «сервер занят, попробуйте через
минуту». Пароль удаляется после шага 2 при любом исходе и по TTL; вместе с ним по TTL удаляется временный HOME
нового Apple ID (§7).

**Успех.** Новый Apple ID → строки `users`/`accounts` (§5), временный HOME → `accounts/<id>`. Известный →
обновить `name`, `storefront`, `session=ok`, `session_since`, сбросить `expired_mail_sent` — задания в
ожидании продолжаются. Устройство получает cookie `appshelf_auth` на год:
`<user_id>:<epoch>:<expires>:<HMAC(cookie-key, user_id \0 epoch \0 expires)>`; активной полкой становится
этот Apple ID.

### Сессия панели и токен магазина

Независимы. Токен истёк → баннер на полке и «Войти заново» на «Мои Apple ID» (тот же вход с подставленным
адресом, без приглашения). Каждый вход в панель заодно обновляет токен магазина этого ID.

### Полки, выход, запасная ссылка

- Активная полка — cookie `appshelf_acct` (id Apple ID); не принадлежит вошедшему или удалён → первая по id.
- «Выйти» — удалить cookie на этом устройстве. «Выйти везде» — `users.epoch += 1`. Удалённый человек — cookie
  не действует (нет строки).
- Запасная ссылка: владелец создаёт для человека (в т. ч. для себя) → `/l/<токен>`, одноразовая, 24 ч → cookie
  `appshelf_auth` этого человека без Apple. CLI `appshelf login-link --email <Apple ID>` печатает такую же
  ссылку — для владельца, у которого нет ни живой cookie, ни работающего входа Apple. *Уточнение 2026-10-09:*
  GET `/l/` только показывает кнопку «Войти как …», ссылка расходуется POST — превью мессенджеров открывают
  ссылки сами.

### Лимиты

- Общий: 10 неудачных попыток любого вида (неизвестный ID, неверный пароль или код, плохая ссылка) за минуту →
  минуту вход не принимается (как сейчас).
- На Apple ID: 5 ответов Apple `invalid_credentials` за час → вход этим ID закрыт до часа с первой неудачи
  («…закрыт, попробуйте через N мин»: сервер живёт в UTC, время на часах вводило бы в заблуждение). Отказы на edge, таймауты и `busy` не считаются. Счётчики — в памяти процесса
  (перезапуск обнуляет; один процесс — §11).
- Для Apple ID идёт скачивание → вход ждёт его блокировку не дольше 10 с → «Идёт скачивание для этого
  Apple ID — попробуйте через пару минут». Скачивания других Apple ID вход не задерживают.

## 5. Данные

SQLite, версия схемы — `PRAGMA user_version` (было 0, станет 2).

| Таблица | Поля |
|---|---|
| `users` | `id` PK AUTOINCREMENT, `name`, `role` (`owner`/`member`), `invite_id`, `created_at`, `epoch` |
| `accounts` | `id` PK AUTOINCREMENT, `user_id`, `email` UNIQUE, `name`, `storefront`, `session` (`none`/`ok`/`expired`), `session_since`, `expired_mail_sent`, `device_mac` (`''` — настоящий MAC сервера), `legacy_pub` (0/1), `last_login_at`, `created_at`; со схемы 3 — `shelf`, `shelf_next` (токен каталога, §5 «Архив») |
| `links` | `id` PK, `kind` (`invite`/`login`), `token_hash` UNIQUE (SHA-256 hex), `label`, `user_id` (у `login` — кому), `created_at`, `expires_at`, `used_at`, `disabled_at` |
| `purchases` | + `account_id`; PK `(account_id, app_id)` |
| `apps` | + `account_id`; PK `(account_id, app_id)` |
| `removed_checks` | + `account_id`; PK `(account_id, app_id)` |
| `versions` | + `account_id` |
| `jobs` | + `account_id` (у всех видов, включая `refresh_history` и `check_removed`) |
| `state` | только общее: `nightly_last`, `nightly_result`, `low_space_mail_sent` |

`AUTOINCREMENT` у `users` и `accounts` — id не переиспользуется: по id строятся HOME и каталог архива, а
недоудалённые файлы прежнего владельца id не должны достаться новому.

### Архив

`<архив>/<токен учётки>/<app_id>-<версия>/{app.ipa, manifest.plist, icon.png}`;
токен учётки = `HMAC-SHA256(PUB_TOKEN, "account:<id>")`, первые 32 hex. У `legacy_pub = 1` — сам `PUB_TOKEN`
(нынешний каталог, без переноса файлов и пересборки manifest). `dir_in_use` и имена каталогов версий — в
пределах Apple ID. `PUB_TOKEN` по-прежнему только в `appshelf.env` и имени каталога владельца.

*Уточнение 2026-10-09 (схема 3):* токен учётки — случайные 32 hex в `accounts.shelf`; каталоги с HMAC
`appshelf-web` при старте переименовывает и правит в них manifest (`jobs.move_shelves`, новый токен сначала в
`accounts.shelf_next` — прерванный перенос доделывается). `appshelf rotate-token --email` даёт полке новый токен
так же, в том числе полке `legacy_pub`.

### Удаление

- Человек удаляет свой Apple ID (страница подтверждения): строки полки, каталог в архиве, HOME ipatool. Был
  последним — удаляется и человек.
- Владелец удаляет человека — то же для всех его Apple ID.
- Последний Apple ID владельца удалить нельзя.

## 6. Переход с версии 1

Выполняется при первом открытии базы новым кодом (`appshelf-web` или ночная проверка), одной транзакцией
`BEGIN IMMEDIATE`; `user_version` проверяется внутри транзакции — второй процесс ждёт и видит готовую схему.

1. Создать `users`, `accounts`, `links`; пересоздать таблицы с новым ключом, скопировать строки с
   `account_id = 1`.
2. Есть данные (строки в `purchases`/`apps` или `state.session` не пуст) → владелец (`users.id = 1`,
   `owner`) и Apple ID `accounts.id = 1`: `email` = `APPSHELF_OWNER`, `name`/`storefront`/`session`/
   `session_since`/`expired_mail_sent` — из `state`, `device_mac = ''`, `legacy_pub = 1`. Ключи из `state`
   удалить.
3. Данные есть, `APPSHELF_OWNER` пуст → исключение, служба не стартует, в журнале «задайте APPSHELF_OWNER —
   Apple ID владельца нынешних данных».
4. Данных нет → пустая схема v2; владелец появится при первом входе `APPSHELF_OWNER`. Нет и его → `/login`
   отвечает «Сервер не настроен: не задан APPSHELF_OWNER».

`deploy.sh`: создать `/etc/appshelf/accounts` (`appshelf`, 0700) и `<data>/locks`; если есть
`/etc/appshelf/.ipatool`, а `accounts/1` нет — перенести в `accounts/1/.ipatool` (шифрование учётки от пути не
зависит, вход не нужен); проверить, что `APPSHELF_OWNER` задан. Файл `web-auth` и команда
`set-web-password` удаляются.

## 7. ipatool

### Патч `05-device-mac`

Переменная окружения `IPATOOL_DEVICE_MAC` (12 hex, разделители `:`/`-` допускаются) заменяет обнаружение MAC
в `device_mac_address()`; оттуда её получают `guid`, `kbsync`, `fserial`. Адрес-заглушка
(`is_placeholder_mac`) или не 6 байт → выход `1`, JSON `{"error": "bad_device_mac", …}`, к Apple не
обращаемся. Переменной нет — поведение прежнее.

### MAC нового Apple ID

Выдаётся при первом входе, хранится в `accounts.device_mac`: префикс производителя Apple (OUI из реестра IEEE;
список префиксов — константа, сверенная с реестром при реализации) + 3 случайных байта. Перенесённый ID —
`''`, переменная не передаётся.

### Запуск

`Ipatool` — на Apple ID: `HOME = <APPSHELF_IPATOOL_HOME>/accounts/<id>`, `IPATOOL_DEVICE_MAC` (если задан),
блокировка `<data>/locks/<id>.lock`, общий `IPATOOL_PROXY`. Первый вход нового ID — во временный HOME
`accounts/.new-<16 hex>/` (0700) со свежим MAC; успех → `rename` в `accounts/<id>`, отказ или TTL → удалить.

### Блокировки

- На Apple ID — внутри каждого вызова ipatool, как сейчас общая: вход ждёт ≤ 10 с, остальное — сколько нужно.
- Общая на скачивание `<data>/locks/download.lock` — вокруг `download` в `fetch_version`: в один момент
  качается один IPA, проверка «свободно ≥ 4 ГБ» остаётся верной. Порядок взятия: скачивание → Apple ID;
  блокировку Apple ID никто не держит, ожидая скачивания.
- Рабочие каталоги: `tmp/web/dl-<account>-<app>`, `tmp/nightly/…`.

## 8. Задания и ночная проверка

- **Обработчик** (один поток в `appshelf-web`) берёт задания Apple ID с `session = ok`: `publish` →
  `refresh_history` → `check_removed`, внутри — по `id` (кто раньше нажал). `check_removed` уступает
  публикациям любого Apple ID (как сейчас — своим). `SessionExpired` → `expired` только у этого ID, его
  задания ждут.
- **Ночная проверка** обходит Apple ID с `session = ok` по `id`: история → справочник удалённых → новые
  версии (как сейчас для одного). Ошибка или истёкший токен останавливает только свой ID.
  `nightly_result` — строка на ID (`<email>: обновлено N, без изменений M, ошибок K; …`), `nightly.stamp` —
  в конце.
- **Справочник удалённых:** полная перепроверка (`full=True`) — когда `account_id % 7 == weekday()` даты
  прогона; в остальные ночи — только непроверенные (`full=False`).
- `requeue_running`, `fail_stale_updates`, `has_active_jobs` — с учётом `account_id`; `/api/status` —
  только задания и приложения активного Apple ID.

## 9. Письма (`MAIL_TO`)

| Событие | Письмо |
|---|---|
| Истёк вход Apple ID **владельца** | одно на эпизод на каждый ID (`accounts.expired_mail_sent`), в тексте — какой ID |
| Мало места | как сейчас (`state.low_space_mail_sent`) |
| Новый участник | имя, Apple ID, подпись приглашения |

Участники писем не получают — баннер в панели.

## 10. Экраны

Шаблоны Jinja2, вёрстка под iPhone, как сейчас.

1. **Вход `/login`** (без шапки). Шаг 1 — Apple ID, пароль; плашка приглашения; «Пароль на сервере не
   сохраняется». Шаг 2 — код; подсказка: «Apple покажет запрос входа с картой — на ней город сервера, а не ваш.
   Нажмите „Разрешить“ и введите код». Тексты ошибок — §4 и прежние (`edge_rejected`, `timeout`).
2. **Шапка.** Каталог · История · Удалённые · Apple ID · Участники (владелец). Справа — активный Apple ID и
   состояние входа; при нескольких ID — список для переключения (`/acct/<id>`); «Выйти».
3. **Каталог, История, Удалённые** — как сейчас, для активного Apple ID; баннер «Вход в Apple ID … истёк» со
   ссылкой «Войти заново». Подсказка в каталоге: «На iPhone в App Store должен быть выполнен вход этим же
   Apple ID — иначе приложение при запуске попросит пароль».
4. **Мои Apple ID `/apple`.** Строка на ID: адрес, имя, витрина, состояние и с какого времени, место. «Войти
   заново», «Удалить» (страница подтверждения «Удалить полку … (N ГБ)?»). Ниже — «Добавить Apple ID» и
   «Выйти на всех устройствах».
5. **Участники `/admin`** (владелец). *Приглашения:* подпись, дата, сколько пришло, активна/отключена;
   «Создать ссылку» (подпись) — ссылка показывается **один раз**; «Отключить». *Люди:* имя, роль, Apple ID
   (адрес, состояние, последний вход, место); «Ссылка входа» (показывается один раз), «Выйти везде»,
   «Удалить» (страница подтверждения).

Без пароля: `/healthz`, `/pwa/`, `/login`, `/join/`, `/l/`; `/d/` — Apache, как сейчас. Без всплывающих
окон JavaScript; JavaScript — только опрос `/api/status`.

## 11. Безопасность и ошибки

- `account_id` — только из серверной сессии; `app_id` в адресах ищется в пределах активного ID, чужой → 404.
  `/admin` и действия владельца проверяют роль на сервере, участник → 403.
- Пароль Apple ID — stdin ipatool и память ≤ 10 минут; не в файлах, логах, `jobs.error`, argv.
  Незавершённый вход привязан к cookie браузера.
- Ссылки — `secrets.token_urlsafe(32)`, в базе SHA-256; сравнение — поиском по хэшу.
- Неизвестный Apple ID без приглашения до Apple не доходит: сервер не проверяет пароли посторонних.
- Компромисс: «не зарегистрирован» и «неверный пароль» различаются — по ответу видно, есть ли адрес на сервере.
  Для закрытого круга приемлемо: иначе человек без приглашения не поймёт, что ему нужно.
- Проверка `Origin` у POST — как сейчас. `appshelf-web` — строго один процесс uvicorn: незавершённые входы и
  счётчики лимитов — в его памяти.

| Ситуация | Поведение |
|---|---|
| Вход нового Apple ID не удался или брошен | временный HOME удалён, строк нет |
| Приглашение отключили между шагами | отказ, временный HOME удалён |
| Нет `APPSHELF_OWNER` при переходе с данными | служба не стартует, причина в журнале |
| `bad_device_mac` | «Сбой настройки сервера», подробности в журнале |
| Запасная ссылка использована или просрочена | «Ссылка недействительна — попросите новую» |
| Удаление Apple ID или человека, архив недоступен | отказ «Архив недоступен — удалить сейчас нельзя», ничего не удаляется: IPA с данными покупателя не должен остаться без хозяина |

## 12. Тестирование

pytest, быстрый набор ≤ 60 с, время — только подменой (`now`, `clock`, дата прогона).

- **Переход:** база v1 с данными → v2, строки с `account_id = 1`, владелец и ID 1 из `state`; без
  `APPSHELF_OWNER` — исключение; повторное открытие ничего не меняет; пустая база → v2 без владельца.
- **Изоляция:** два Apple ID у двух людей; каталог, история, удалённые, `/api/status`, publish/retry/unpublish
  с чужим `app_id` → 404 и чужие строки не тронуты; участник на `/admin` → 403; cookie выбора чужой полки
  игнорируется.
- **Вход:** известный ID; неизвестный без приглашения — подставной ipatool не вызван; по приглашению; по
  `APPSHELF_OWNER` (и не работает, когда владелец уже есть); «Добавить Apple ID»; TTL удаляет пароль и
  временный HOME; приглашение отключено между шагами → отказ; шаг 2 с чужой cookie `appshelf_login` → отказ.
- **Сессии и ссылки:** `epoch` гасит cookie; cookie удалённого человека не действует; запасная ссылка —
  одноразовая и истекает; в базе нет сырого токена.
- **Лимиты:** 5 × `invalid_credentials` → ID закрыт на час, через час открыт; `edge_rejected` не считается;
  20 незавершённых входов → отказ 21-му.
- **ipatool:** у нового ID свой HOME и `IPATOOL_DEVICE_MAC`, у перенесённого переменной нет; вход B не ждёт
  блокировку A; два скачивания идут по одному; MAC нового ID — с OUI из списка и не заглушка.
- **Задания и ночь:** истёкший токен одного ID не останавливает другие; порядок `publish` разных ID;
  полная перепроверка справочника — только в свой день недели.
- **Письма:** о новом участнике; об истечении — только по ID владельца, одно на эпизод на ID.
- **Архив:** токен по HMAC, у `legacy_pub` — `PUB_TOKEN`; URL в manifest — с токеном своего ID; удаление ID
  удаляет его каталог.
- `integration` (на сервере): `IPATOOL_DEVICE_MAC=<адрес> ipatool kbsync --dsid 1 --debug` (без обращения к
  Apple) — в stderr `device ID: OK (IPATOOL_DEVICE_MAC)`; заглушка — выход `1`, `bad_device_mac`.
- `manual`: §13, шаг 1; после выкладки — критерии успеха 1, 2, 5, 7 на живых устройствах.
